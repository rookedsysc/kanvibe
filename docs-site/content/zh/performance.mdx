# 性能基准测试

在模拟 SSH 往返延迟（RTT）为 60 毫秒的环境中，粘贴 280 KB 并收到远端确认的中位耗时从 **556 毫秒降至 124 毫秒**，连续输入 8 个字符并收到回显的中位耗时从 **487 毫秒降至 61 毫秒**。在 Pane 聊天中，Claude 执行 `/clear` 后可以再次发送消息的耗时从 **1,215 毫秒降至 63 毫秒**，首次打开聊天到显示第一行对话的耗时从 **354 毫秒降至 170 毫秒**。单次按键到屏幕显示回显的 p95 在基准版中为 115.0 毫秒，在同时包含看板和远程改进的合并版中为 115.8 毫秒。

## 远程终端

### 比较了哪些版本？

2026 年 11 月 26 日，我们以同一个 KanVibe 修订版本（`6e7ceb7a3220`）为起点，在独立的 worktree 中构建了四个发布版本。**看板改进版**减少了卡片移动和渲染时的重复计算与复制（`d194e50d4c38`）。**远程改进版**允许 PTY 和 Herdr 套接字在等待确认期间按顺序发送最多 8 个数据块（`568f66d03259`）。**合并版**包含这两项改进。

### SSH 传输耗时

下表为 RTT 设为 60 毫秒时的中位耗时，单位为毫秒。280 KB 粘贴测试以远端 shell 读完 280,000 字节并返回字节数为终点。Herdr 一行测量等量二进制数据经过 KanVibe 的 SSH 套接字转发路径往返所需的时间。

| 操作 | 基准版 | 看板改进版 | 远程改进版 | 合并版 |
| --- | ---: | ---: | ---: | ---: |
| PTY 单字符回显 | 61.0 | 60.9 | 60.9 | 60.9 |
| PTY 连续 8 字符回显 | 486.7 | 487.0 | 61.0 | 61.0 |
| PTY 粘贴 280 KB 并确认接收 | 555.5 | 552.5 | 124.4 | 124.4 |
| Herdr 套接字 280 KB 回显 | 553.5 | 550.7 | 123.2 | 123.0 |
| 直接使用 OpenSSH 管道的单字符回显 | 60.6 | 60.5 | 60.5 | 60.6 |

下表对比了基准版与远程改进版在不同模拟延迟下的中位耗时，单位为毫秒。

| 设定 RTT | 连续 8 字符回显，基准版 → 远程改进版 | 粘贴 280 KB，基准版 → 远程改进版 |
| --- | ---: | ---: |
| 0 毫秒 | 2.2 → 0.4 | 10.2 → 7.1 |
| 60 毫秒 | 486.7 → 61.0 | 555.5 → 124.4 |
| 120 毫秒 | 969.1 → 120.9 | 1093.0 → 243.6 |

连续输入测试一次发送 8 个字符，中途无需等待回显。四个版本的单字符回显耗时都接近一次网络往返，多个字符进入发送队列时差异更明显。

### 屏幕响应

每个单元格为中位数 / p95，单位为毫秒。p95 表示约 95% 的样本在该时间内完成。按键耗时从注入 X11 输入到绘制终端回显的画面为止。卡片拖放耗时从松开鼠标到卡片出现在目标列为止。

| 操作 | 基准版 | 看板改进版 | 远程改进版 | 合并版 |
| --- | ---: | ---: | ---: | ---: |
| 远程 PTY 按键到屏幕，RTT 60 毫秒 | 99.4 / 115.0 | 99.4 / 115.7 | 97.3 / 115.6 | 83.9 / 115.8 |
| 本地 tmux 按键到屏幕 | 19.2 / 51.8 | 19.8 / 51.7 | 19.8 / 63.2 | 19.8 / 61.3 |
| 默认看板，松开卡片到屏幕显示 | 35.7 / 52.7 | 37.7 / 50.3 | 38.2 / 57.9 | 38.9 / 51.9 |
| 新增 240 张卡片，松开卡片到屏幕显示 | 103.1 / 117.1 | 95.5 / 124.4 | 104.6 / 130.0 | 96.1 / 122.0 |

在卡片更多的看板上，看板改进版与合并版的拖放中位耗时下降，p95 则上升。两项指标对看板响应速度的结论并不一致。

### 测试环境

- 在 Linux 上用 Bubblewrap 隔离应用和测试服务器，每个场景限制为 2 个 CPU 核心、2 GiB 内存且无交换空间。隐藏 GPU 设备，由 llvmpipe 在 1600 × 1000 的 Xvfb 虚拟显示器上渲染。
- 每个场景中，四个版本固定使用同一组 CPU 核心并交替调整运行顺序。预热后，每个版本从 4 次运行中收集 48 个按键样本与 24 个卡片拖放样本。SSH 传输测试针对每个版本和 RTT 组合收集 24 个单字符样本，连续输入和批量传输分别收集 8 个样本。
- 使用临时 OpenSSH 服务器和双向延迟代理。代理只增加延迟。Herdr 的结果覆盖套接字转发，直接 OpenSSH 的结果覆盖管道往返。真实网络的丢包、Herdr 和 Ghostty 的完整画面延迟以及显示器物理输出延迟均在此次测量范围之外。

## Pane 聊天连接

Pane 聊天以聊天视图显示终端 pane 中运行的 AI CLI 的对话，并把消息发送给该 CLI。下表中的“可以发送”指 KanVibe 确认了 pane 中的 CLI 和对话、聊天输入可以发送到该对话的时刻。

### 比较了哪些版本？

我们比较了同一基准修订版本（`6e7ceb7a3220`）的发布构建，以及在其上加入 Pane 聊天改进（`6b8c4b8fd09f` 至 `7bfefd2d6601`）的构建。改进版做了以下变更：

- 在 Linux 上检查 pane 中是否运行着 CLI 时，不再多次扫描完整的进程列表，而是一次只读取 pane shell 的后代进程。单次检查从 22–60 毫秒降至 3.6 毫秒。
- CLI 报告新的对话 ID 后，立即重新检查该 pane，而不是等待下一次 1–1.5 秒的轮询。
- 打开聊天时先绘制最新的 12 行，其余行在下一帧绘制。
- 首次输入前的新 Claude 对话，以及 `/clear` 后尚无消息的 Claude 记录，会作为空的新对话连接，而不再打开所有项目的记录。KanVibe 不会借用其他对话的记录。

### 测量结果

每个单元格为中位数 / p90，单位为毫秒。p90 表示约 90% 的样本在该时间内完成。在对话记录中选择会话一行只统计了中位数。

| 操作 | 基准版 | 改进版 | 样本数 |
| --- | ---: | ---: | ---: |
| 首次打开聊天 → 第一帧 | 33.7 / 34.2 | 34.1 / 34.4 | 10 |
| 首次打开聊天 → 第一行对话 | 353.9 / 370.2 | 169.6 / 178.0 | 10 |
| 从终端切回聊天 → 显示对话 | 123.1 / 123.2 | 59.1 / 59.2 | 20 |
| 从终端切回聊天 → 可以发送 | 203.0 / 203.1 | 139.1 / 171.1 | 20 |
| 从看板回到任务 → 显示对话 | 498.5 / 506.6 | 138.6 / 154.6 | 10 |
| 在对话记录中选择会话 → 显示消息 | 155.8 | 139.7 | 10 |
| 检测到 CLI 会话 → 可以发送（自动打开） | 340.1 / 346.4 | 104.4 / 112.1 | 10 |
| `/clear` → 可以发送 | 1215.4 / 1247.4 | 62.7 / 63.8 | 30 |
| `/resume` → 可以发送 | 1279.9 / 1296.3 | 78.9 / 80.0 | 20 |

首次打开聊天时两个版本的第一帧相同，之后填充对话所需的时间缩短。打开对话记录视图在交替测量中为 55.7 毫秒 → 71.7 毫秒，慢了一帧。两个版本绘制该视图的成本都是 20–27 毫秒，用最终提交重新测量为 55.7 毫秒。我们判断这是因为点击恰好与每秒读取一次 pane 布局后的整窗重绘重叠。

### 使用真实的 Claude Code 确认

我们在 tmux pane 中运行真实的 Claude Code 2.1.332，基准版和改进版各确认一次。数值为从 Claude 把对话 ID 写入会话文件（`~/.claude/sessions/`）到聊天连接到该对话的时间，单位为毫秒。

| 操作 | 基准版 | 改进版 |
| --- | ---: | ---: |
| 开始新对话 → 可以发送 | 774 | 80 |
| `/clear` → 连接到新对话 | 690 | 69 |
| `/resume` → 连接到之前的对话 | 774 | 80 |

在从未运行过 Claude 的文件夹中，基准版会打开所有项目的记录文件，连接耗时约 4 秒；改进版为 80 毫秒。在同一文件夹的两个 pane 中运行 Claude 时，也确认了每个聊天只显示自己 pane 的对话。

### 测试环境

- 在 Linux 上用 Xvfb 显示器以及隔离的 HOME、XDG 和 tmux 套接字路径运行发布构建。未固定 CPU，也未限制内存，测量期间的平均负载为 0.1–2。
- 重复测量使用了一个测试用 CLI，它像真实的 Claude 2.1.332 一样写入会话文件，并模拟 `/clear` 和 `/resume`。续接的对话记录为 4 MB。基准版和改进版交替运行至少 10 轮，没有失败。用最终提交再测的 10 次中，所有操作都在 ±5% 以内。
- 真实 CLI 的确认每种组合只运行一次。Codex 0.172.0 不是已验证对话识别方式的版本（0.169.0），因此按设计保持未连接。Zellij pane 中的 Claude 在两个版本中都没有自动连接，因此未测量。Herdr、Gemini CLI 和 OpenCode 未使用真实 CLI 测量。
