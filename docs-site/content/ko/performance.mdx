# 성능 벤치마크

SSH 왕복 지연(RTT) 60ms를 재현한 환경에서 280KB를 붙여넣고 원격 수신을 확인하기까지 중앙값이 **556ms에서 124ms**로, 연속 8자 입력은 **487ms에서 61ms**로 줄었습니다. Pane 채팅에서는 Claude의 `/clear` 뒤 다시 메시지를 보낼 수 있기까지가 **1,215ms에서 63ms**로, 채팅을 처음 열어 첫 대화 줄이 보이기까지가 **354ms에서 170ms**로 줄었습니다. 한 글자가 입력된 뒤 화면에 표시되기까지의 p95는 기준판 115.0ms, 보드·원격 변경을 모두 적용한 합본 115.8ms로 차이가 없었습니다.

## 원격 터미널

### 무엇을 비교했나요?

2026년 11월 26일에 같은 KanVibe 소스(`6e7ceb7a3220`)를 기준으로 네 판을 독립 worktree에서 릴리스 빌드했습니다. **보드 변경판**에는 카드 이동과 렌더링 중 중복 계산·복사를 줄이는 변경(`d194e50d4c38`)을 적용했습니다. **원격 변경판**에는 PTY와 Herdr 소켓에서 수신 확인을 기다리는 동안 최대 8개 조각을 순서대로 보낼 수 있게 한 변경(`568f66d03259`)을 적용했습니다. **합본**에는 두 변경을 모두 적용했습니다.

### SSH 전송 시간

아래 값은 RTT를 60ms로 설정했을 때의 중앙값(ms)입니다. 280KB 붙여넣기는 원격 셸이 280,000바이트를 읽고 수신량을 회신할 때까지 쟀습니다. Herdr 행은 KanVibe가 사용하는 SSH 소켓 중계를 통해 같은 크기의 바이너리 데이터를 왕복시킨 결과입니다.

| 작업 | 기준판 | 보드 변경판 | 원격 변경판 | 합본 |
| --- | ---: | ---: | ---: | ---: |
| PTY 한 글자 에코 | 61.0 | 60.9 | 60.9 | 60.9 |
| PTY 연속 8자 에코 | 486.7 | 487.0 | 61.0 | 61.0 |
| PTY 280KB 붙여넣기 수신 확인 | 555.5 | 552.5 | 124.4 | 124.4 |
| Herdr 소켓 280KB 에코 | 553.5 | 550.7 | 123.2 | 123.0 |
| 직접 OpenSSH 파이프 한 글자 에코 | 60.6 | 60.5 | 60.5 | 60.6 |

아래는 지연 조건을 바꿔 시험한 기준판과 원격 변경판의 중앙값(ms)입니다.

| 설정 RTT | 연속 8자 에코, 기준판 → 원격 변경판 | 280KB 붙여넣기, 기준판 → 원격 변경판 |
| --- | ---: | ---: |
| 0ms | 2.2 → 0.4 | 10.2 → 7.1 |
| 60ms | 486.7 → 61.0 | 555.5 → 124.4 |
| 120ms | 969.1 → 120.9 | 1093.0 → 243.6 |

연속 입력 시험은 에코를 기다리지 않고 8자를 보냈습니다. 한 글자 에코는 네 빌드 모두 네트워크 왕복 지연에 가까웠고, 여러 글자가 대기열에 들어가는 경우에 전송 차이가 크게 나타났습니다.

### 화면 응답

각 값은 중앙값 / p95(ms)입니다. p95는 측정값의 약 95%가 그 시간 안에 들어왔다는 뜻입니다. 키 입력은 X11 입력 주입부터 터미널 에코를 그린 프레임까지, 보드는 마우스를 놓은 시점부터 대상 열에 카드가 표시될 때까지 측정했습니다.

| 작업 | 기준판 | 보드 변경판 | 원격 변경판 | 합본 |
| --- | ---: | ---: | ---: | ---: |
| 원격 PTY에서 키 입력 → 화면, RTT 60ms | 99.4 / 115.0 | 99.4 / 115.7 | 97.3 / 115.6 | 83.9 / 115.8 |
| 로컬 tmux에서 키 입력 → 화면 | 19.2 / 51.8 | 19.8 / 51.7 | 19.8 / 63.2 | 19.8 / 61.3 |
| 기본 보드의 카드 드롭 → 화면 | 35.7 / 52.7 | 37.7 / 50.3 | 38.2 / 57.9 | 38.9 / 51.9 |
| 카드 240개를 추가한 보드의 드롭 → 화면 | 103.1 / 117.1 | 95.5 / 124.4 | 104.6 / 130.0 | 96.1 / 122.0 |

카드가 많은 보드에서는 보드 변경판과 합본의 드롭 중앙값이 낮아졌고 p95는 높아졌습니다. 보드 응답이 일관되게 빨라졌다고 판단하기에는 결과가 엇갈립니다.

### 측정 환경

- Linux에서 Bubblewrap으로 앱과 테스트 서버를 격리하고 CPU 2코어, 메모리 2GiB, 스왑 0으로 제한했습니다. GPU 장치를 숨기고 Xvfb의 1600×1000 화면을 llvmpipe로 렌더링했습니다.
- 각 시나리오에서는 네 빌드를 같은 CPU 코어에 고정하고 실행 순서를 교대했습니다. 화면 응답은 워밍업 후 빌드당 4개 세션에서 키 입력 48회와 카드 드롭 24회씩을 집계했습니다. SSH 전송은 각 빌드와 RTT의 조합에서 워밍업 후 단일 키 24회, 연속 입력과 280KB 전송은 항목당 8회를 집계했습니다.
- 임시 OpenSSH 서버와 양방향 지연 프록시를 사용했습니다. 프록시는 지연만 추가합니다. Herdr는 소켓 전송 구간을, 직접 OpenSSH는 파이프 왕복 구간을 잰 값입니다. 실제 인터넷의 패킷 손실, Herdr나 Ghostty의 전체 화면 표시, 모니터 표시 지연은 측정 범위 밖입니다.

## Pane 채팅 연결

Pane 채팅은 터미널 pane에서 실행 중인 AI CLI의 대화를 채팅 화면으로 보여 주고, 그 CLI로 메시지를 보냅니다. 아래 표의 "보낼 수 있음"은 KanVibe가 pane의 CLI와 대화를 확인해 채팅 입력이 그 대화로 전송될 수 있게 된 시점입니다.

### 무엇을 비교했나요?

같은 기준 소스(`6e7ceb7a3220`)의 릴리스 빌드와, 여기에 Pane 채팅 변경(`6b8c4b8fd09f`부터 `7bfefd2d6601`까지)을 적용한 빌드를 비교했습니다. 변경판은 다음을 바꿨습니다.

- pane에서 CLI가 실행 중인지 확인할 때 프로세스 목록 전체를 여러 번 훑던 방식을, Linux에서는 pane 셸의 자손 프로세스만 한 번에 읽도록 바꿨습니다. 확인 한 번의 비용이 22~60ms에서 3.6ms로 줄었습니다.
- CLI가 새 대화 ID를 알리면 1~1.5초 조회 주기를 기다리지 않고 그 pane을 바로 다시 확인합니다.
- 채팅을 열 때 최신 12줄을 먼저 그리고, 나머지 줄은 다음 프레임에 그립니다.
- 첫 입력 전의 새 Claude 대화와 `/clear` 직후 아직 메시지가 없는 Claude 기록을, 모든 프로젝트 기록을 열지 않고 빈 새 대화로 연결합니다. 다른 대화의 기록을 대신 쓰지는 않습니다.

### 측정 결과

각 값은 중앙값 / p90(ms)입니다. p90은 측정값의 약 90%가 그 시간 안에 들어왔다는 뜻입니다. 대화 기록에서 세션을 고르는 구간은 중앙값만 집계했습니다.

| 작업 | 기준판 | 변경판 | 측정 횟수 |
| --- | ---: | ---: | ---: |
| 채팅 처음 열기 → 첫 프레임 | 33.7 / 34.2 | 34.1 / 34.4 | 10 |
| 채팅 처음 열기 → 첫 대화 줄 | 353.9 / 370.2 | 169.6 / 178.0 | 10 |
| 터미널에서 채팅으로 다시 전환 → 대화 줄 | 123.1 / 123.2 | 59.1 / 59.2 | 20 |
| 터미널에서 채팅으로 다시 전환 → 보낼 수 있음 | 203.0 / 203.1 | 139.1 / 171.1 | 20 |
| 보드에서 태스크로 다시 들어옴 → 대화 줄 | 498.5 / 506.6 | 138.6 / 154.6 | 10 |
| 대화 기록에서 세션 선택 → 메시지 표시 | 155.8 | 139.7 | 10 |
| CLI 세션 감지 → 보낼 수 있음(자동 열기) | 340.1 / 346.4 | 104.4 / 112.1 | 10 |
| `/clear` → 보낼 수 있음 | 1215.4 / 1247.4 | 62.7 / 63.8 | 30 |
| `/resume` → 보낼 수 있음 | 1279.9 / 1296.3 | 78.9 / 80.0 | 20 |

채팅을 처음 열 때 첫 프레임은 두 빌드가 같았고, 그 뒤 대화가 채워지기까지의 시간이 줄었습니다. 대화 기록 화면을 여는 구간은 교차 측정에서 55.7ms → 71.7ms로 한 프레임 늦게 나왔습니다. 화면을 그리는 비용은 두 빌드 모두 20~27ms로 같았고, 최종 커밋으로 다시 잰 값은 55.7ms였습니다. 1초마다 pane 배치를 읽은 뒤 창 전체를 다시 그리는 시점과 클릭이 겹친 결과로 판단했습니다.

### 실제 Claude Code에서 확인

tmux pane에서 실제 Claude Code 2.1.332를 띄워 기준판과 변경판을 각 1회 확인했습니다. 값은 Claude가 세션 파일(`~/.claude/sessions/`)에 대화 ID를 쓴 시점부터 채팅이 그 대화에 연결되기까지의 시간(ms)입니다.

| 작업 | 기준판 | 변경판 |
| --- | ---: | ---: |
| 새 대화 시작 → 보낼 수 있음 | 774 | 80 |
| `/clear` → 새 대화로 연결 | 690 | 69 |
| `/resume` → 이전 대화로 연결 | 774 | 80 |

Claude를 처음 실행하는 폴더에서는 기준판이 모든 프로젝트의 기록 파일을 열어 연결까지 약 4초가 걸렸고, 변경판은 80ms였습니다. 같은 폴더에서 Claude를 두 pane에 띄웠을 때도 각 채팅이 자기 pane의 대화만 보여 주는 것을 확인했습니다.

### 측정 환경

- Linux에서 릴리스 빌드를 Xvfb 화면과 격리한 HOME·XDG·tmux 소켓 경로로 실행했습니다. CPU 고정이나 메모리 제한은 두지 않았고, 측정 중 부하 평균은 0.1~2였습니다.
- 표의 반복 측정에는 실제 Claude 2.1.332처럼 세션 파일을 쓰고 `/clear`·`/resume`을 흉내 내는 시험용 CLI를 썼습니다. 이어 연 대화 기록은 4MB입니다. 기준판과 변경판을 한 번씩 번갈아 10회 이상 실행했고 실패는 없었습니다. 최종 커밋으로 다시 잰 10회도 모든 구간이 ±5% 안에 들었습니다.
- 실제 CLI 확인은 각 조합에서 1회만 실행했습니다. Codex 0.172.0은 대화를 정확히 식별하는 방식을 확인한 버전(0.169.0)이 아니어서 의도대로 연결되지 않았습니다. Zellij의 Claude pane은 두 빌드 모두 자동으로 연결되지 않아 측정하지 않았습니다. Herdr, Gemini CLI, OpenCode는 실제 CLI로 측정하지 않았습니다.
