독자: KanVibe Pane Chat 코드를 아는 개발자. 이 계획의 범위와 테스트 선택을 승인하려는 사람

Pane Chat 지연 개선에서 남긴 후속 4건을 리서치 실측에 맞춘 범위로 나눴고, 승인 전에 정할 것은 열린 결정 4개와 테스트 선택 12개다.

  • 코드가 바뀌는 것은 둘이다. Zellij pane의 root PID를 환경 변수로 찾고(F1), 배치가 그대로이면 다시 그리지 않는다(F3).
  • 나머지 둘은 테스트와 fixture만 바꾼다. Herdr 첫 실행 화면을 설정으로 끄고(F2), 신뢰 화면 순서를 시나리오로 고정한다(F4).
  • F4는 전제가 재현되지 않았다. Claude 2.1.332는 신뢰를 수락한 0.11초 뒤에 세션 기록을 쓰므로 제품 코드는 바꾸지 않는다.

건별 범위: 무엇을 고치고 무엇을 남기는가

각 건은 원인, 고른 방법, 범위에서 뺀 것의 순서로 적는다. 수치는 Linux, Zellij 0.46.0, Herdr 0.9.5, Claude Code 2.1.332에서 잰 값이다.

F1 Zellij: root PID를 pane 환경 변수로 찾는다

Zellij에서 채팅이 자동으로 열리지 않는 이유는 KanVibe가 pane의 root PID를 얻지 못해서다. read_zellij_surface는 list-panes JSON의 terminal_pid와 pid를 읽는데, Zellij는 이 값을 주지 않는다. root PID가 없으면 CLI 확인이 "CLI 없음"으로 끝나고 자동 열기 확인이 통과하지 못한다.

Zellij 서버는 pane 프로세스를 띄울 때 ZELLIJ_PANE_ID를 환경에 넣는다. 격리 서버에서 pane 0, 1, 2, 3, 5의 값이 list-panes의 id와 모두 같았다. pane 안에서 띄운 자손도 같은 값을 물려받으므로, 서버의 직접 자식으로 좁혀야 root 하나가 남는다. 아래 그림은 pane 5를 찾는 예다.

고른 방법은 다음과 같다.

  • D1: root는 명령줄에 --server가 있는 zellij 프로세스의 직접 자식 가운데, 환경의 ZELLIJ_SESSION_NAME과 ZELLIJ_PANE_ID가 모두 같은 프로세스다. 정확히 하나일 때만 쓴다. 0개나 2개 이상이면 지금처럼 None이다.
  • D2: 조회는 /proc만 읽는 POSIX sh 스크립트 하나다. pgrep을 쓰면 40.4ms, /proc만 읽으면 14.2ms였다. list-panes 한 번은 18.9ms다.
  • D3: surface를 읽을 때 고른 pane 하나만 조회한다. 1초마다 도는 배치 조회에서는 생략한다. JSON에 PID가 있으면 그 값을 먼저 쓴다.
  • D4: 범위는 자동으로 열리고 대화가 보이는 데까지다.

세션 이름으로 서버를 직접 찾지 않는 이유가 있다. Zellij 0.46.0은 소켓 파일 이름이 세션 이름이 아니라 불투명 ID다. 그래서 서버 명령줄에는 세션 이름이 없고, 자식의 ZELLIJ_SESSION_NAME으로 맞춘다.

아래는 조회 스크립트의 뼈대다. 제안이며 아직 구현하지 않았다.

session=$1
pane=$2
for comm in $(grep -lxF -e zellij /proc/[0-9]*/comm 2>/dev/null); do
  server=${comm#/proc/}
  server=${server%/comm}
  tr '\0' '\n' < "/proc/$server/cmdline" | grep -qxF -e --server || continue
  # 서버의 직접 자식만 읽는다. 자손은 같은 값을 물려받아도 대상이 아니다.
  children=$(cat /proc/$server/task/*/children 2>/dev/null)
  for child in $children; do
    grep -qzxF -e "ZELLIJ_PANE_ID=$pane" "/proc/$child/environ" || continue
    grep -qzxF -e "ZELLIJ_SESSION_NAME=$session" "/proc/$child/environ" || continue
    echo "$child"
  done
done

범위에서 뺀 것은 둘이다.

  • 전송과 선택 카드. 전송은 입력란 상태가 Ready여야 하는데 Zellij surface는 커서와 화면을 읽지 않는다. 채팅은 열리고 대화는 보이지만 보내기는 계속 막힌다. OQ2에서 정한다.
  • macOS. /proc가 없어 스크립트가 아무것도 출력하지 않고 지금 동작을 유지한다. OQ1에서 정한다.

검토한 다른 방법은 모두 탈락했다.

방법 탈락 이유
list-panes -c, list-clients, 세션 메타데이터 PID가 없다(실측)
플러그인 API get_pane_pid wasm 플러그인 배포와 ReadApplicationState 권한 창이 필요하다. Zellij 전역 부작용이라 환경 안전 규칙과 충돌한다
서버 소켓 직접 통신 비공개 프로토콜이다

F2 Herdr: fixture가 첫 실행 화면을 끄고 서버를 정리한다

Herdr 실제 CLI 검증이 막힌 이유는 fixture에 Herdr 설정 파일이 없어서다. fixture는 XDG_CONFIG_HOME을 격리하고, 그 아래 herdr/config.toml이 없으면 Herdr가 첫 실행 화면을 띄운다. 격리 세션에서 그 화면은 키 입력을 pane에 넘기지 않았다. 그 화면의 Enter는 통합 설치를 시도했으므로 키 입력으로 넘기는 방식은 쓰지 않는다.

D5로 fixture가 아래 내용을 xdg/config/herdr/config.toml에 미리 쓴다. 이 설정으로 띄운 격리 세션에서는 화면이 뜨지 않았고 입력이 pane에 들어갔다.

onboarding = false

[update]
version_check = false
manifest_check = false

[ui.sound]
enabled = false

함께 고칠 fixture의 빈틈은 둘이다.

  • multiplexer_bin_dirs()가 tmux와 zellij만 PATH에 넣는다. herdr를 더한다.
  • 종료 처리가 tmux만 끈다. D6으로 fixture 환경 안에서 실행 중인 Herdr 세션을 이름으로 session stop, session delete한다. 리서치 중에 13시간 남은 고아 서버를 실제로 봤다.

KanVibe의 Herdr 경로가 받는 값은 명령 수준에서 확인했다. pane process-info가 shell_pid를 주고, 그 값으로 읽은 프로세스 표에서 가짜 Claude가 판정 조건에 맞았다. 앱을 띄운 끝단 확인은 아직 하지 않았고 이번 계획의 T6과 T12가 맡는다.

화면 기준 이미지는 바뀌지 않는다. 기준 상태 가운데 Herdr task의 터미널을 여는 상태가 없기 때문이다.

F3 다시 그리기: 상태가 바뀐 때만 알린다

터미널 화면을 보는 동안 1초마다 창 전체를 다시 그리는 이유는 배치 조회가 끝날 때마다 무조건 notify하기 때문이다. GPUI는 notify된 view의 조상을 모두 dirty로 표시하고, 앱에는 캐시된 view가 없다. 다시 그리기 한 번은 약 31ms다.

D7로 finish_layout의 시작과 끝에서 네 값을 비교해 달라졌을 때만 notify한다.

비교하는 값 화면에서 쓰이는 곳
layout 채팅 덮개의 위치, 전환 버튼, 연결 화면
is_layout_failed 아래쪽 안내 문구
is_chat_focused 작업 상세가 터미널에 포커스를 줄지 판단
focused_pane 포커스된 pane이 사라졌을 때의 초기화

나머지 변화는 이미 각자 notify한다. 포커스 복원과 toggle 완료는 focus_pane이, 자동 열기 확인 결과는 probe_pane이, 자식 화면의 가시성은 set_visible이 알린다.

상황 지금 변경 후
배치가 그대로인 조회 조회마다 창 전체를 다시 그린다 다시 그리지 않는다
배치 변경, 조회 실패, 포커스 pane 소멸 다시 그린다 다시 그린다

이 건은 그림 없이 표로 충분하다. 전후 차이가 한 줄이기 때문이다.

F4 신뢰 화면: 제품 코드는 그대로 두고 순서를 테스트로 고정한다

채팅이 신뢰 화면 위로 열린다는 전제는 재현되지 않았다. 자동 열기는 대화 연결이 필요하고, 연결 증거인 세션 기록은 신뢰를 수락한 뒤에 생긴다. 아래 그림은 실제 Claude 2.1.332에서 잰 순서다.

실측은 두 조건에서 했다. 일반 폴더에서는 25초, hook을 선언한 git 저장소에서는 36초 동안 신뢰 화면을 띄워 뒀고 그동안 세션 기록이 없었다. SessionStart hook도 수락 뒤에만 실행됐다.

화면 자체도 선택 카드로 읽히지 않는다. 선택지에 번호가 없고 기본 강조가 No, exit다. 저장소의 read_claude_prompt를 그대로 복사해 이 화면에 돌린 결과는 null이었다.

그래서 D8로 제품 코드는 바꾸지 않는다. 대신 두 가지로 순서를 고정한다.

  • 가짜 Claude에 신뢰 대기 모드를 넣는다. 신뢰 화면 글을 그리고 Enter 전에는 세션 기록을 쓰지 않는다. 그동안 채팅이 열리지 않는지 끝단에서 본다(T10).
  • 실제 Claude로 같은 순서를 1회 확인한다(T12). Claude 버전을 올릴 때 다시 돌릴 항목이다.

범위에서 뺀 것은 둘이다.

  • 신뢰 질문을 채팅 카드로 보여 주는 안. 번호가 없어 숫자 키로 고를 수 없고, 기본값이 No, exit라 잘못 보내면 CLI가 종료된다.
  • 신뢰 화면 문구를 읽어 자동 열기를 막는 방어 코드. 재현되지 않은 상황을 위한 코드다. OQ3에서 정한다.

  • OTQ1 (F3): "유휴 상태에서 다시 그리지 않는다"를 끝단에서 무엇으로 판정할지 정해야 한다. 지금 성능 표식에는 일반 프레임마다 나오는 표식이 없다. A는 T8의 notify 횟수와 기존 구간 10회 재측정이다. B는 측정 도구에 유휴 프레임 수 표식을 추가하는 것이다. C는 A에 수동 CPU 관찰을 더하는 것이다. 권장은 A다.

남는 위험: 이번에 검증하지 못하는 것

계획대로 끝내도 아래는 확인되지 않은 채 남는다.

  • macOS. Zellij root 조회가 동작하지 않고 지금 동작을 유지한다. OQ1이 B가 되어도 Mac 실측이 필요하다.
  • SSH 원격. 이 머신에서 localhost SSH 인증이 되지 않아 원격 실행을 재지 못했다. 근거는 기존 프로세스 표 스크립트와 같은 전달 방식이라는 점뿐이다.
  • 세션 이름을 바꾼 Zellij 세션. 기존 pane은 옛 이름을 유지하므로 조회가 실패하고 지금처럼 연결되지 않는다. 잘못된 대상에 연결하지는 않는다.
  • 래퍼로 실행한 Zellij. 프로세스 이름이 zellij가 아니면 서버를 찾지 못한다. 역시 연결되지 않는 쪽으로 실패한다.
  • F3의 암묵적 의존. 다른 화면이 1초 다시 그리기에 기대고 있었다면 갱신이 멈춘다. 그런 의존은 찾지 못했고 화면 기준 캡처로 확인한다.
  • Claude의 버전 변화. 세션 기록을 쓰는 시점이 신뢰 전으로 당겨지면 F4의 전제가 바뀐다. T12를 버전마다 다시 돌려 잡는다.
