# KanVibe 터미널에서 직접 실행한 Codex에 옵션을 붙이는 방법

사용자가 KanVibe 터미널에서 평소처럼 `codex`를 입력하고, 그 실행에만 `tui.status_line`의 `thread-id`를 더하는 방법을 조사했다. **KanVibe가 관리하는 새 셸의 `PATH` 맨 앞에 `codex` 래퍼를 두면 가능하다.** 셸은 기존대로 명령을 해석한다. 래퍼는 해석된 인자를 받아 실제 Codex를 실행한다.

## 어느 지점에서 명령을 받아야 하는가

| 방법 | 범위 | 판정 |
| --- | --- | --- |
| pane 전용 `PATH` 래퍼 | 관리하는 셸에서 `PATH`로 찾는 `codex` | 직접 입력, 히스토리 실행, 스크립트 등 같은 이름으로 찾는 실행에 적용된다. 절대 경로와 우선순위가 높은 셸 함수는 래퍼를 거치지 않을 수 있다. |
| 셸 함수 `codex()` | 함수를 등록한 대화형 셸 | 이미 열린 셸에도 사용자가 직접 불러올 수 있다. bash·zsh 등의 초기화 방법이 다르고, 기존 alias·함수 및 `command codex` 경로를 고려해야 한다. |
| 셸의 `preexec`·명령 감지 | 셸에서 실행 직전 관찰 | 실행할 명령이나 인자를 교체하는 인터페이스는 아니다. 터미널에 표시할 메타데이터 수집에 쓸 수 있다. |
| 터미널의 Enter에서 입력 재작성 | KanVibe가 받은 키 입력 | 셸 프롬프트와 실행 중인 TUI를 구분해야 한다. 줄 편집, 히스토리, 여러 줄 붙여넣기, 명령 치환까지 셸과 맞춰야 한다. 적용 범위에 비해 복잡하다. |
| 워크트리 `.codex/config.toml` | 신뢰된 워크트리에서 Codex를 시작할 때 | Codex 설정으로 상태줄을 표시한다. 사용자가 직접 친 명령에도 적용되며 워크트리 단위의 선택 기능에 적합하다. |

zsh는 슬래시가 없는 명령을 셸 함수, 내장 명령, `PATH` 순으로 찾는다. bash도 별도 경로가 없는 외부 명령을 `PATH`에서 찾고 결과를 캐시한다. 래퍼는 정상 명령 조회 과정에서 선택된다.

> [zsh 명령 실행](https://raw.githubusercontent.com/zsh-users/zsh/zsh-5.9/Doc/Zsh/exec.yo) "the shell searches each element"
> [Bash 명령 조회](https://tiswww.case.edu/php/chet/bash/bashref.html) "Bash performs a full search"

zsh의 `preexec`에는 이미 실행할 명령 문자열이 인자로 들어온다. VS Code도 셸 초기화와 통합 스크립트를 사용해 명령을 감지한다. KanVibe GPUI의 현재 키 처리 경로는 인코딩한 시퀀스를 터미널에 쓰므로 이 단계에서 입력 전체를 다시 해석하는 데 드는 비용이 크다. [KanVibe 터미널 입력 코드](../../crates/kanvibe-app/src/views/task_detail/terminal/pane.rs)

> [zsh 특수 함수](https://raw.githubusercontent.com/zsh-users/zsh/zsh-5.9/Doc/Zsh/func.yo) "Executed just after a command has been read"
> [VS Code 셸 통합](https://code.visualstudio.com/docs/terminal/shell-integration) "command detection"

Codex는 신뢰된 프로젝트의 `.codex/config.toml`을 읽는다. `-c`는 해당 실행의 설정을 덮어쓰고, `tui.status_line`은 상태줄에 표시할 항목 배열이다. 사용자가 선택한 상태줄을 유지하려면 배열에서 기존 항목을 보존한 채 `thread-id`를 추가해야 한다. 사용자가 명령에서 상태줄을 직접 지정했으면 그 값을 우선한다.

> [Codex 프로젝트 설정](https://learn.chatgpt.com/docs/config-file/config-advanced#project-config-files-codexconfigtoml) "only when the project is trusted"
> [Codex CLI 옵션](https://learn.chatgpt.com/docs/cli/reference) "take precedence for that invocation"
> [Codex 설정 레퍼런스](https://learn.chatgpt.com/docs/config-file/config-reference) "Ordered list of TUI footer status-line item identifiers"

## 래퍼를 어떤 범위에 적용하는가

예를 들어 사용자가 `codex resume <ID>`를 입력하면 래퍼는 `resume`과 ID를 원래 인자 그대로 넘긴다. 래퍼는 자기 자신을 다시 찾지 않도록 다음 실행 파일을 찾아 절대 경로로 `exec`한다. 실행할 Codex는 해당 셸이 사용하는 환경을 기준으로 찾는다. 대화형 실행에만 상태줄 설정을 적용한다. `exec`, `--help` 같은 비대화형 경로와 사용자 지정 상태줄 값은 그대로 넘긴다. 첫 인자만으로 모든 Codex 실행을 구별할 수 없으므로, 초기 옵션과 서브커맨드가 섞이는 경우도 구현에서 다뤄야 한다.

새 로컬 PTY는 자식 환경을 지정할 수 있다. tmux·Herdr·Zellij는 실제 pane 셸을 멀티플렉서가 만든다. KanVibe가 붙는 클라이언트 PTY에만 래퍼 경로를 추가하면 이미 떠 있는 pane 안의 셸에는 전달되지 않는다. tmux에서 확인한 지점은 새 창의 자식 셸이다. Herdr·Zellij·SSH는 실제 호스트의 pane 생성 경로에서 별도로 확인해야 한다. [KanVibe PTY 생성](../../crates/kanvibe-terminal/src/pty/native.rs) · [KanVibe 멀티플렉서 연결](../../crates/kanvibe-terminal/src/terminal_registry/spawn_local.rs) · [KanVibe 런타임 환경 규칙](../../CLAUDE.md)

## 새 pane에 래퍼를 붙인다는 말은 무엇인가

사용자가 연동을 켠 뒤 새 pane을 열면, KanVibe는 그 pane의 실제 셸 프로세스를 생성할 때만 래퍼 경로가 앞에 있는 `PATH`를 전달한다. 부모 앱에서 전역 환경을 바꾸거나 사용자 셸 설정 파일을 편집할 필요는 없다. 아래는 새 셸을 띄울 때의 개념 예시다.

```bash
env "PATH=/path/to/kanvibe-wrappers:$PATH" /bin/zsh
```

그 셸에서 사용자 입력 `codex`는 `/path/to/kanvibe-wrappers/codex`에 먼저 도달한다. 래퍼는 래퍼 자신을 제외한 실제 Codex 실행 파일을 찾고, 원래 인자와 상태줄 옵션을 전달한다. tmux를 붙이는 경우에는 KanVibe가 띄운 tmux 클라이언트와 tmux 서버가 만드는 실제 pane 셸이 서로 다르다. 환경은 후자에 전달해야 한다. 이 방식은 아직 KanVibe에 구현되지 않은 후보다.

## 상태줄이 밀리면 대화 연결은 어떻게 되는가

Codex 0.172.0은 상태줄이 화면 너비보다 길면 줄을 나눈다. 상태줄에 배정된 화면 높이가 부족하면 마지막 표시 줄을 줄임표로 자른다. 스크린샷에 ID가 없다는 사실만으로 ID 항목을 설정했는지, 뒤에서 잘렸는지 판단할 수 없다.

> [Codex 0.172.0 상태줄 렌더러](https://github.com/openai/codex/blob/rust-v0.172.0/codex-rs/tui/src/bottom_pane/status_line.rs#L136-L155) "more_rows"

연결이 상태줄에만 의존하면 ID가 잘리거나 가려진 동안 KanVibe가 현재 대화를 확정할 수 없다. 이때 최초 연결은 대기로 남긴다. 이미 연결했던 대화가 있더라도 화면을 읽지 못했다는 이유만으로 이전 대화에 계속 전송하지 않는다. 같은 대화임을 다른 검증 경로에서 확인하거나 ID가 다시 보이면 전송을 활성화할 수 있다.

현재 Rust 파서는 지정된 줄에 UUID만 있거나 UUID 뒤에 정해진 메인 대화 표시가 붙은 형식만 읽는다. 따라서 `model · UUID`는 화면에 전부 보이더라도 현재 파서의 기대 형식과 다르다. 더구나 현재 판독 지원 목록은 0.169.0만 포함한다. [KanVibe 상태줄 판독기](../../crates/kanvibe-ai/src/pane_chat/codex_display.rs) · [대상 재확인](../../crates/kanvibe-terminal/src/pane_chat/service/conversation.rs)

상태줄을 사용한다면 `thread-id`를 맨 앞에 두고, 여러 항목이 들어간 경우와 좁은 pane에서 실제 판독을 확인한다. 가장 단순한 첫 검증은 `tui.status_line=["thread-id"]`다. 순서를 바꾸거나 ID만 표시해도 아주 좁은 pane에서 UUID 전체가 보인다는 보장은 없다. 화면 폭과 관계없이 연결해야 하면 KanVibe가 제어하는 대화 생성·재개 응답 등 별도 경로에서 ID를 받아야 한다.

## 직접 입력 검증에서 무엇을 확인했는가

실제 Codex 대신 받은 인자를 JSON으로 출력하는 임시 실행 파일을 사용했다. 로컬 bash와 zsh에서 각각 10개 경우를 확인했다. `codex`와 `command codex`가 래퍼를 거쳤다. 재개와 포크에서 공백·한글 인자가 보존됐다. `exec`, 도움말, 사용자 지정 상태줄, 절대 경로 호출, 기존 셸 함수도 확인했다.

같은 bash·zsh 셸에서 `codex()` 함수를 정의하면 다음 `codex` 호출부터 적용됐다. `command codex`는 두 셸 모두에서 함수를 건너뛰고 실행 파일을 찾았다.

격리한 tmux 3.8 서버에 창을 만들고 `codex` 키 입력과 Enter를 보냈다. 일반 창, `new-window -e PATH=…`만 준 창, `env PATH=…`로 자식 셸을 시작한 창, 명령을 보낸 비접속 클라이언트의 PATH를 바꾼 창을 비교했다. 뒤의 두 창에서만 래퍼가 실행됐다. tmux는 pane 환경을 조립한 뒤 비접속 클라이언트의 PATH가 있으면 그 값으로 덮어쓸 수 있다. pane 범위의 실험에서는 자식 셸에 환경을 직접 넘기는 방식이 확실했다.

> [tmux 3.8의 pane 환경 조립](https://github.com/tmux/tmux/blob/3.8/spawn.c#L408-L428) "only unattached clients"

이 실험은 명령 선택과 인자 전달을 검증했다. 실제 KanVibe에서 Codex 상태줄을 읽고 세션을 연결하는 검증은 별도로 필요하다. 특히 화면에서 ID가 보인다는 사실과 KanVibe가 해당 버전을 지원한다는 사실은 따로 확인해야 한다. 현재 작업 트리의 판독 허용 버전은 0.169.0이다. [KanVibe의 Codex 상태줄 버전 판정](../../crates/kanvibe-ai/src/pane_chat/codex_display.rs)

## KanVibe에 적용한다면

일반적으로 직접 친 `codex`를 유지해야 하므로, 사용자가 켠 **관리 pane 전용 래퍼**를 후보로 둔다. 래퍼는 각 pane 셸이 생성되는 곳에서 붙이고 기존 pane은 관찰 경로를 사용한다. 이미 열린 셸에 즉시 적용할 필요가 있다면 사용자가 그 셸에서 연동을 명시적으로 불러오는 방법이 있다. 그 pane에서 어떤 명령이 실제 실행되는지는 셸의 `type -a codex`로 확인할 수 있다.

KanVibe는 래퍼가 호출됐다는 사실로 세션을 확정하지 않는다. 래퍼는 실행 옵션을 붙인다. KanVibe는 해당 pane에 표시된 대화 ID를 읽고, 새로운 대화나 재개로 ID가 바뀌면 전송 대상을 다시 확인한다.
